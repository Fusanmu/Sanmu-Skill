# 个人游戏评测成文

把已经稳定的观点写成可以直接发布的文章。追求的不是“句句像金句”，而是选材有轻重、措辞准确、段落有变化，读起来像一位认真玩过游戏的人在论坛上把自己的判断说清楚。

本 Skill 是成文编辑，不是采访者或研究员。若与 `interview-game-review` 配合，后者负责采访、观点账本、证据边界、外部盲点扫描与立场确认，本 Skill 接收它整理好的材料后开始写作。单独调用时，直接使用用户给出的旧对话、笔记、立场卡或旧稿，不要让用户重走采访流程。

## 按需读取参考

- 每次写稿或重写前读取 [voice-profile.md](references/voice-profile.md) 与 [prose-craft.md](references/prose-craft.md)。
- 需要拟主标题、小标题或重组章节时读取 [title-and-section-craft.md](references/title-and-section-craft.md)。
- 需要理解用户如何修改 AI 初稿，或校准“像用户”与“模仿错字”的边界时读取 [before-after.md](references/before-after.md)。
- 完整长评交稿前读取 [quality-rubric.md](references/quality-rubric.md)，并完成其中的硬门槛。

不要为了形式一次加载所有参考。按任务读取，但完整成稿至少需要声音、文笔、标题与质检四项。

## 识别任务

根据材料直接进入最靠后的可执行阶段，不展示模式菜单：

- **从材料成文**：已有采访、观点账本或立场卡，尚无完整稿件。
- **结构重写**：已有稿件，但重心平均、段落模板化或判断关系没写清楚。
- **文笔精修**：结构与事实基本稳定，重点改善标题、段落、句子和遣词。
- **标题专项**：只处理主标题或小标题，不改正文事实和观点。
- **终稿复核**：只查保真、AI 套路、文字卫生和发布质量。

若材料来自另一条 Codex 会话，先读取那条会话中已经完成的采访、确认与成稿；不要依据会话标题猜内容。只补问会改变文章的硬约束，例如目标平台、剧透边界或期望篇幅。缺少某个具体例子时，宁可保留概括或标记待确认，也不发起一轮完整采访。

## 成文工作流

### 1. 固定事实与声音边界

先在内部建立“写作底稿”，不必原样展示给用户：

```text
文章用途与读者：
一句话判断：
最重要的两至四个内容块：
明确可写的第一人称体验：
可中性补充的已核实事实：
只能保守表达或不得写入的内容：
用户原话或自然表达锚点：
标题与剧透边界：
明确要求的章节顺序：
每节唯一主题：
标题格式：
剧透章节位置：
功能章节位置：
不得合并的内容：
```

外部评测中未经用户采纳的观察不进入底稿。材料若含互相冲突的说法，以用户最近一次明确确认或人工终稿为准；无法判断且会影响结论时再询问。

以上六项构成“结构合同”。用户明确要求一节一事、指定章节顺序、标题格式、剧透位置或单独保留评分、购买推荐、结语时，逐项照办。它们优先于“减少章节”“改变段落数量”“让标题组合更有变化”等一般编辑建议；不得以文笔优化为由擅自合并。

逐条保护以下内容：平台、版本、进度、经验背景、具体例子、人物称谓与代词、评价谓词、强度、适用人群和推荐结论。润色不拥有改变这些内容的权限。用户明确自称“资深玩家”时，不要为了显得谦逊改成“很熟悉”或“玩过一些”；人物代词没有可靠来源时，重复名字或身份，不根据外形、名字和印象补写“他／她”。

### 2. 决定主轴与篇幅权重

文章不能把所有栏目平均分配。先判断用户花费最多语言、举例最具体、评价最强或反复回到的内容；它应成为最长、最具体的核心章节。次要优缺点可以合并、压短或只用一段。

为每节写一行内部映射：

```text
章节作用｜核心判断｜可用材料｜自然起点｜段落运动｜合适的落点｜禁止推出的内容
```

相邻章节不要重复相同的段落运动。完整长评若有四个以上非功能性章节，内部映射至少使用三种不同运动；也要有意识地改变段落数量，避免连续四节都用“三段式”。结构必须由这款游戏和这位用户的关注点决定；不强制“玩法—剧情—视听—缺点—总结”，也不为完整性补齐用户不关心的栏目。已经核实的事实不等于必须进入正文；记忆模糊、没有明显问题、又不影响总评或购买判断的补充项可以完全不写。

### 3. 先写正文骨架，再拟标题

先用普通但准确的句子写出正文骨架，确保每段都有信息增量。此时不追求修辞。正文稳定后再拟主标题和小标题，避免漂亮标题反过来绑架内容。

正文要交替使用 [prose-craft.md](references/prose-craft.md) 中不同的段落运动，让观察、例子、判断、影响、保留意见与读者边界自然接续。允许章节停在具体影响、普通判断或一句保留意见上，不必每节升华。

### 4. 做一次真正的文笔编辑

文笔编辑按以下顺序进行：

1. 删除重复意思和为结构服务的空句。
2. 调整信息顺序，让因果、转折和限定自然出现。
3. 用准确动词和具体名词替换空泛评价。
4. 改变连续相同的句长、段长和开头方式。
5. 只在材料允许时使用具体细节；不靠虚构场景制造生动。
6. 保留少量用户自己的口语连接和评价方式，修正错字与明显语病。

删除重复意思，不等于删除所有再次表态。允许前言给出评价坐标、评分章节解释依据、结语落下推荐；三处可以重申同一总评，但必须各自增加不同功能，不能逐字复述或换同义词原地打转。

默认避开“不是／并非／没有／不只是……而是／却是／更是”这类二元洞见骨架，尤其禁止在开头和第一节用它制造中心句。`未必……却……`、`看似……其实……`、`不一定……但……`、`不再只是／不再只剩……` 若承担同样的“先压低一端再宣布洞见”，也按同一问题处理，不能只换连接词。也避免反复使用“真正……”“更重要的是”“归根结底”“这也正是”“某种意义上”。发现后先改成直接陈述、顺承关系、让步关系或具体影响，不用另一套同义模板替换。

### 5. 生成并筛选标题

按 [title-and-section-craft.md](references/title-and-section-craft.md) 在内部生成多组候选。主标题至少覆盖直述、核心体验、条件判断三种方向；材料中存在可追溯的视觉或叙事意象时，再加入意象型候选。小标题先追求具体和准确，再考虑节奏。

默认只交付评分最高的一组主标题与小标题。用户明确要挑选时，再给三至五组差异清楚的候选，并说明各自侧重。不得用用户没有确认的主题、隐喻、心理变化或营销承诺换取“吸睛”。

把直述型和判断型候选去掉 Markdown 标记后当作普通中文朗读一遍。`先立住新昆仑`、`难度压在长战`、`后期开始发力` 这类为了短而压缩出来的搭配，只要脱离标题语境便不自然，就直接淘汰。意象型标题可以是短语，不强求成为完整句，但每个意象都必须能指向材料中的明确画面、叙事元素或用户确认表达，不能用“余韵、回响、灵魂”等通用词代替内容。叙事主题是全文主轴时，标题要写出人物、选择、前后关系或可追溯的核心意象，不能只放一个抽象词加世界名称。

### 6. 保真回读

逐句检查所有第一人称体验、心理变化和因果，尤其是：

`让我`、`使我`、`令我`、`推动我`、`我意识到`、`我才明白`、`我终于`、`我开始`、`我愿意`、`我印象最深`

每一处都必须能回指用户原话或明确确认。回查时在内部写出对应原句；只有相邻观点、主题相近或情绪方向一致不算来源。`结局很震撼` 不等于 `通关后还会继续想`，`有印象` 不等于 `会反复想起`。主题分析、常识、外部评测和“这样写更顺”都不能替代来源。找不到语义等强的来源时，改成中性事实、降低为用户确实说过的程度，或删除。

检查是否把“还可以”升级成“流畅”，把“有印象”升级成“忘不掉”，把“喜欢”解释成未经确认的原因，或为人物、玩法和美术分配了整齐但虚构的心理作用。

同时检查“撑起／撑住整段流程”“让评价往上走”“演出方式起了很大作用”“这才是给高分的主要原因”等抽象因果。它们常把几个已确认的单项评价重新编排成用户没有说过的作用关系。除非材料明确确认这层因果，否则拆回各自的具体判断。

删除没有信息增量的标准评测句，例如“起到了应有的作用”“成熟的类型框架”“作品自己的味道”“功能完整，衔接也顺”。也不要从一个具体例子自行推出“比单纯调数值更容易让人记住”。这些句子看似稳妥，往往同时造成媒体稿语气和软编造。

严格守住材料的范围。一个 Boss 的战前选择有意思，不足以推出所有 Boss “不只靠数值制造压力”；用户认为提示已经够用、不构成缺点，也不足以补写“保留了自行寻找的空间”。局部例子只能支撑该例子的判断，缺少便利没有自动附带设计收益。

范围控制必须留在编辑幕后，通过准确主语和选材完成。不要在正文里写“这个例子只对应这一场战斗”“没必要据此概括所有 Boss”“我不打算把它写成优点”“没有需要单独提醒的问题”等防守性说明；这些句子是在向检查器交代工作，不是在评价游戏。改成范围准确的正文，或整段删除。

### 7. 执行终稿文件闭环

在可读写文件的环境中，完整长评必须先写入工作区内的 UTF-8 暂存 `.md` 文件，再检查并从同一文件交付。暂存文件只用于内部验证，不等于用户要求保存成品，也不得覆盖用户原稿。

严格按顺序执行：

1. 把准备交付的完整正文写入暂存文件；标题、正文和结尾全部包含在内。
2. 使用本 Skill 自己的脚本检查该文件。Windows 环境优先启用 UTF-8：

```text
$env:PYTHONUTF8='1'
python -B <skill-root>/scripts/prose_check.py <暂存稿.md>
```

3. 退出码非零时不得交付。逐条处理所有硬错误；逐条回查每个提醒的确切材料来源，能修改得更自然时就修改，只有来源明确、力度相同且表达不可替代时才保留。
4. 每次改动暂存稿后重新运行检查。旧报告对新文本无效。
5. 逐句朗读同一文件，检查脚本难以发现的错词、代词、主语范围和语义跳跃；例如不能把地图上的“标记”误写成“标点”。
6. 检查通过并完成 [quality-rubric.md](references/quality-rubric.md) 的人工门槛后，以 UTF-8 重新读取这个确切文件，把文件内容原样作为终稿。检查之后不得只在回复框里临时改字；任何修改都会使检查失效。

用户要求“只输出正文”只是不展示检查过程，绝不允许跳过文件、脚本或人工回读。若环境确实无法写文件，可把确切终稿通过标准输入传给脚本；若脚本无法执行，不得声称是可直接发布的终稿。

脚本报告是预警，不代替人工判断，重点处理：

- Unicode 替换字符、乱码迹象或异常控制字符
- 二元对比骨架
- 高风险第一人称心理与因果
- 反复出现的洞见套话
- 过分整齐的段落或章节收尾
- 抽象、口号化、强行工整的标题风险
- 连续使用“初入／深入／后期”等阶段词批量生成的小标题；`地图：判断`、`战斗：判断` 这类“对象：判断”本身不构成问题
- 连续章节使用相同段落数量与展开顺序
- 同义二元结构、空泛媒体句和未经确认的评分因果
- 从局部例子扩大到整个系统、替缺少便利补写设计收益、把较弱体验升级成后续心理结果

最终检查没有成功完成、暂存文件与交付文本不一致，或任一人工硬门槛未通过，都不得交付为终稿。

### 8. 交付

默认交付一版已经处理完的推荐稿，不同时附上未经处理的初稿，也不要求用户再调用“去 AI 味”工具才能发布。用户未限制输出时，简短说明本次主要编辑选择和仍需确认的事实；用户要求只要正文时，直接交付经过文件闭环的正文，不展示报告。研究来源不属于本 Skill 的产物。

只有用户明确要求时才写入文件、覆盖原稿、生成论坛格式或执行 Git 操作。调用本 Skill 本身不授权提交和推送。

## 不可越过的边界

- 不重新进行外部评测搜索，也不擅自把“全面”当成补写所有栏目。
- 不新增亲历场景、心理活动、因果解释、人物动机或评价强度。
- 不把人工终稿中的错字、病句、重复和排版疏漏当作个人风格。
- 不机械复制样文里的签名句、口头禅、标题格式或结尾。
- 不把论坛玩家的声音抛光成标准媒体通稿，也不故意塞网络词假装自然。
- 不用隐喻、对仗、金句和二元反转代替具体判断。
- 不为了标题更漂亮改变正文主轴，不为了章节整齐平均分配篇幅。
- 不把结构合同、证据边界或检查器规则解释给正文读者；规则只负责约束成稿。
- 不以脚本零警告作为文章好看的充分条件；脚本只能发现部分问题。
