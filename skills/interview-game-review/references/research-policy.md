# 外部评测扫描与核验规则

## 启动时点

先完成用户原始体验采访和初步观点整理，避免媒体主题提前塑造用户立场。之后按文章类型决定深度：

- **完整中长评、通关评测、购买建议与深度文章**：默认执行多源盲点扫描。
- **短评或用户明确只要个人随感**：只核验必要事实，或按用户要求缩减扫描。
- **版本再评、持续更新、DLC、性能或购买信息**：额外确认评测时点、平台和版本差异。
- **用户记忆不确定或外部出现强反例**：针对核心论点继续核验。

用户明确不想做外部对照时跳过。网络不可用时说明缺口，不用模型记忆假装查过。

## 来源层级

1. **第一方事实**：游戏官网、开发者公告、补丁说明、官方商店、平台支持页面。
2. **直接材料**：用户截图、游戏内文本、版本号、性能记录、实际菜单或设置。
3. **专业媒体**：用于理解不同评测角度，不把单家观点当成事实。
4. **玩家社区**：Steam 近期／全部评价、NGA、贴吧、Reddit、论坛等，用于发现具体问题和争议，不代表总体玩家。

关键事实尽量回到第一方页面。记录来源、发布日期、适用版本和直接打开状态。搜索摘要只能作为线索，不能作为充分证据。

## 扫描范围

“尽可能全面”指尽量覆盖本作的重要体验维度和不同立场，不是把所有来源或栏目塞进文章。根据游戏类型选择真正相关的维度：

- 核心玩法、操作反馈、战斗或主要循环
- 关卡、地图、探索、谜题、任务与节奏
- 成长、构筑、经济、难度和可访问性
- 叙事、人物、主题、演出与剧透争议
- 美术、音乐、声音与界面
- 平台性能、Bug、版本差异、联机、存档和 Mod
- 重复游玩、流程长度、价格、DLC 与购买条件
- 同系列或同类型作品中的位置

先核验名称、平台、版本和机制等客观事实，再寻找：

1. 用户没有提到但多处出现的具体体验。
2. 用户已经注意到、但可能认为不值得写的内容。
3. 与用户判断相反、且能说明适用条件的观点。
4. 可能来自平台、补丁、难度、流派、进度或系列经验的体验差异。

专业评测应覆盖不同评价方向和侧重点；玩家社区用于发现具体问题、少数体验和版本差异。继续增加来源但新内容主要重复已有观察时停止。单家媒体的独特主题不能冒充共识，也不能因为表达漂亮就成为文章主轴。

## 研究账本

内部为每个候选盲点记录：

```text
维度：
外部观察：
来源与立场：官方事实｜专业评测｜玩家社区
适用条件：平台、版本、难度、进度、流派、系列经验
出现情况：单一来源｜多个独立来源｜相互冲突
与用户原始观点的关系：遗漏｜已注意未写｜支持｜反例｜无关
状态：待询问｜采纳｜注意到但不写｜与体验不符｜仅作背景
```

“多个来源提到”只表示值得询问，不自动证明观点正确或具有代表性。

## 盲点卡与用户筛选

先输出紧凑的“事实卡”和“盲点卡”，不要直接改写用户立场。一次优先给四至六个最可能改变文章的点，其余按需继续：

```text
已核实事实：内容｜直接打开的来源｜日期／版本
候选盲点：外部观察｜具体来源与类型｜单一／多源／冲突｜适用条件
请用户判断：是否遇到｜为什么没提｜要不要写｜影响多大
状态：采纳｜注意到但不写｜与体验不符｜仅作背景｜待回想
```

盲点卡中的“来源”至少写到媒体／社区名称；提供链接不影响阅读时直接附上。把搜索摘要、已打开原文和模型已有知识明确分开。不能只写“多家媒体”或“许多玩家”，却不给用户判断这句话的依据。

用户说“注意到了但不打算提”时，保留在研究账本，不为追求全面强塞进正文。用户说“没注意”时，先邀请回想实际体验；不能仅凭外部评论替用户补出第一人称判断。外部共识不能压过用户体验，文中若提到争议，应准确描述来源和适用条件。

## 防止来源偷渡

- 不把媒体比喻、标题和判断换几个词写成用户原话。
- 不用“大家都认为”“玩家普遍反映”代替可追溯来源。
- 不因评分均值不同而要求用户修改个人评分。
- 不把评论数量、点赞或搜索排序直接解释成代表性。
- 外部观点未经用户确认，不进入第一人称正文；必要时以有来源的背景信息出现。
- 不把媒体文章的标题、主题框架和段落结构移植成用户文章的主轴。
- 研究链接默认放在交稿说明或核验附录；用户没有要求引用时，不在论坛正文末尾自动增加“资料参考”。
