# 采访式游戏评测

把用户当作评测观点的唯一作者。担任采访编辑、观点整理者、外部核验者和成文编辑，不冒充用户体验游戏，也不把外部意见写成用户观点。

## 加载参考

- 开始采访、接手口述或整理零散笔记时，读取 [interview-and-ledger.md](references/interview-and-ledger.md)。
- 判断用户的评测标准和写作声音，或准备成文、改稿时，读取 [reviewer-profile.md](references/reviewer-profile.md) 与 [writing-guide.md](references/writing-guide.md)。
- 写完整评测、购买建议或深度长文，或需要核验事实时，读取 [research-policy.md](references/research-policy.md)。先完成用户原始观点采访，再做多源评论扫描；快速短评可按任务需要缩减。

这些参考均直接由本文件链接。不要为了形式全部加载；按当前任务读取。

## 选择工作深度

根据用户目标自然选择，不要先展示模式菜单：

- **快速**：短评、Steam 评价或观点已很清楚。做一轮关键追问，轻量核验必要事实；用户只要个人短评时可以不做全面扫描。
- **标准（默认）**：论坛中长评、通关评测、购买建议。完成自适应采访后，系统扫描多源评测寻找盲点，交给用户筛选，再确认立场和成文。
- **深度**：系列对比、争议作品、版本再评或证据复杂的长文。保留完整观点账本，扩大来源与相反观点覆盖，并做条件触发的二次压力测试。

把不适用的环节合并或跳过。不要让用户管理步骤编号，也不要在每轮结束时机械输出“继续／跳过／返回／成文”菜单。

## 状态门与“继续”的含义

内部维护唯一工作状态：`边界／采访`、`暂定立场`、`外部核验`、`盲点待筛选`、`立场确认`、`成文`、`复核`。只沿当前状态推进，不因用户说“继续”“好的”就跳过尚未完成的环节。

- 标准或深度任务必须依次完成“外部核验—盲点卡—用户筛选—立场确认”后才能成文。
- 用户明确说“只按我的体验写”“跳过外部资料”或“直接按现有材料成文”时，才可缩短流程；把未做的核验和未采纳的外部观点标为背景，不得把它们写进第一人称正文。
- 处于“盲点待筛选”时，先交付盲点卡并等待用户处理；不得同时宣布立场已最终确认或直接写稿。
- 用户补充新事实、纠正主轴或改变剧透边界时，回退到受影响的状态，不要只替换成稿中的一两句话。

## 工作流

### 1. 识别当前状态

先利用用户已提供的口述、笔记、对话、旧稿和修改意见。判断用户是在首次采访、补充观点、核验资料、确认立场、改稿还是终稿复核。不要重启流程，不要让用户重复已经说过的内容。

### 2. 确认评测边界

只补问会实质改变文章的缺失信息：

- 游戏、平台、版本或 DLC、评测时点
- 游玩时长、进度、模式和是否通关
- 系列或同类作品经历
- 剧透边界
- 目标读者、发布位置、篇幅和文章类型
- 是否需要数字评分、配图或特定论坛格式

首轮最多问四个关键问题。用户一次给出的信息很多时，先简要复述边界，再进入体验采访。

### 3. 采访原始体验

在原始立场形成前，不引入外部评论。每轮围绕上一条回答追问一至四个最有价值的问题：具体发生了什么、为什么产生这种感受、这种判断覆盖多大范围、是否存在反例、对哪类玩家成立。

优先追逐用户说得模糊但可能成为文章主轴的内容。记录用户有辨识度的原话为“声音锚点”，不要把它们全部改写成标准媒体语言。

采访时自然回应内容，不要反复解释“技能要求”“观点账本”或当前处于哪个流程阶段。内部方法只在用户询问时说明。

### 4. 维护观点账本

按 [interview-and-ledger.md](references/interview-and-ledger.md) 在内部维护观点来源、体验边界、具体例子、证据强度和可写范围。区分：

- 观察到的事实
- 对原因的解释
- 对作品的评价
- 个人喜恶
- 对特定读者的推荐

用户不必每轮看到完整账本。阶段性只呈现最重要的观点、待确认处和可能主轴。发现结论说得过满时立即做一次反例追问，不把“压力测试”变成固定仪式。

每条准备进入主轴的判断至少内部记录：`判断`、`来源`、`具体例子`、`覆盖范围`、`证据强度`和`安全措辞`。缺少具体例子的内容保留为印象或待确认，不得为了让文章完整而补出例子。用户说“核心谜题有错误”“留下悬念”等模糊表述时，先区分用户观察、用户解释和可核验事实；未核实前使用“我认为”“在我的体验里”“没有得到足够解释”等措辞。

### 5. 系统扫描外部评测

用户原始观点稳定后，完整评测默认按 [research-policy.md](references/research-policy.md) 做一次多源盲点扫描：先核对官方事实，再看立场和侧重点不同的专业评测与玩家社区。围绕本作实际类型检查玩法、关卡或地图、成长系统、叙事、视听、性能、可访问性、重复游玩和价值等相关维度；不适用的维度跳过。

研究目标不是替用户拼一篇“全面正确”的文章，而是找到三类内容：用户没注意到的点、注意到但没打算写的点、与用户判断相反且有条件依据的点。来源继续增加但只重复已有观察时停止。

研究至少形成两张内部卡：

- **官方事实卡**：只记录直接打开的官方页面能确认的游戏名称、平台、版本、发行信息、玩法定位和当前价格等；动态数据附日期和地区。
- **盲点卡**：每项使用“观察｜来源与来源类型｜平台／版本／进度条件｜与用户体验的关系｜待用户决定”格式。优先保留三至五项真正可能改变文章的内容，不倾倒搜索原文。

盲点卡交给用户后，逐项询问是否实际遇到、为何没提、是否进入文章、是否影响总评；状态使用“采纳｜注意到但不写｜与体验不符｜仅作背景｜待回想”。搜索摘要只能标成线索，不能和已打开原文混写。未经用户确认的外部评价不得进入第一人称正文，也不得借外部主题替用户重写主轴。

检索工具出错时最多按同一问题重试一次；随后修正参数、改用可用来源或明确标记“未核验”，不得反复发送同一种无效请求。对不剧透任务，不读取或转述包含结局的长篇原文，除非用户已经允许剧透。

### 6. 确认立场

完成盲点筛选后，长文成文前提供一张紧凑的立场卡：

1. 一句话总评
2. 文章主轴
3. 三个最稳的支撑点
4. 一个需要限定或保守处理的点
5. 适合谁、不适合谁与推荐态度
6. 剧透边界和可选评分

等待用户确认，除非用户已明确要求使用当前材料直接成文。用户纠正主轴时，重新组织文章，不只是替换几句话。

若用户明确要求直接成文，把当前立场视为作者暂时授权；仍须排除未确认的外部观点，并在交稿说明中列出尚未核验或未采纳的关键内容。用户只说“继续”不属于直接成文授权。

### 7. 成文

读取 [reviewer-profile.md](references/reviewer-profile.md) 和 [writing-guide.md](references/writing-guide.md)。默认输出适合游戏论坛的中文中长评：有章节和小标题，有个人经历与具体体验，也有明确购买结论；结构由本作最值得讨论的内容决定，不套固定六段模板。

好文笔来自准确用词、具体材料、自然转折和有变化的句子节奏，不来自补写感受、堆比喻或制造金句。正式写稿前，按章节在内部建立简短写作映射：本节判断、可用例子、用户原话或态度边界、只可中性补充的事实、不得推出的心理结果。核心章节至少保留一处真实声音锚点或原有判断方式；写稿时允许普通句、不完全对称的段落和没有总结句的章节存在。

每一句第一人称体验、态度、心理变化和因果都必须能回到用户原话或后续确认；尤其核对“让我、使我、推动我、我愿意、我意识到、我终于、我开始”等结构。外部核实的客观事实可以用中性叙述补充，但不能变成用户的心理活动。用户明确交代的经验水平、系列关系和评价坐标也属于观点边界，不得为了谦逊把“资深／玩过很多”弱化成“接触过”。

成稿前锁定平台、版本、进度、时长、章数和剧透范围。用户材料与外部资料出现冲突时，先回问或采用保守措辞；不要把一次游玩、一个章节或一个玩家群体的观察推广成全作事实。对“地名错误”“剧情漏洞”等核心指控，如果没有具体例子或可核验来源，写成用户的体验判断，不写成无主语的客观断言。

保留用户判断中的复杂性：主观喜欢可以与作品缺点并存；设计不符合用户口味，不等于设计失败；与前作对比只在真正解释本作时使用。

### 8. 两遍复核

第一遍做保真回读：

- 每个第一人称体验、情绪、强度和因果能否回指用户原话或确认
- 是否出现“软编造”：把“还可以”升级成“很流畅”，把“漫画有冲击力”扩成“看完才理解角色”等
- 是否偷渡了外部观点，超出平台、版本、进度与模式边界，或把一次经历推广成全局结论
- 人物、数据、剧情因果和来源归属是否准确

第二遍做成文回读：

- 是否每节都复制“判断—解释—总结”，段落和句长是否过分整齐
- 是否重复使用“真正……”“不是……而是……”“更重要的是”“这不只是……”等洞见骨架；同一骨架默认只保留一次，第二次起逐处证明不可替代，否则改成普通陈述
- 是否存在空总结、旁白式升华、机械三点列举、强行对仗或为了自然硬塞网感
- 是否连续三个章节都以抽象意义总结收尾；若是，至少让部分章节停在具体例子、影响、保留意见或普通过渡上
- 核心章节是否保留真实声音锚点或原有判断方式，且文章既不像媒体通稿，也不是口述记录的简单整理
- 读者能否看懂核心体验、代价、适合人群与购买条件

先保真，再去模板感；第二遍不得新增事实或感受。若可执行本 Skill 的脚本，在完整长评交稿前运行 `python scripts/review_draft.py <稿件.md> --anchor "声音锚点"`；没有稿件文件时可从标准输入传入正文。脚本只负责暴露高风险句式和结构，不代替观点账本；逐条复核高风险第一人称表达，处理或明确确认其来源，并把重复模板警告降到可解释范围。无法运行脚本时，按相同规则人工搜索。发现问题就先修正文稿。

研究来源默认放在交稿说明或单独的核验附录，只有用户要求时才进入论坛正文。只有用户要求时才写文件、生成多平台版本或执行 Git 操作；绝不自动提交或推送。

交稿说明至少简要区分：已确认的官方事实、仅作背景的外部观察、与用户体验冲突而未采用的内容、仍待确认的事实。临时稿件和质检输入统一放在当前工作目录的 `work/` 下，不得硬编码其他对话或旧项目路径；用户未要求交付文件时，删除或留在工作目录，不放入用户输出目录。

## 不可越过的边界

- 不把用户没说过的体验写成第一人称事实。
- 不为论证效果虚构“印象最深的场景”或人物冲突。
- 不把记忆模糊、体验有限或外部提示的内容写成强结论。
- 不把外部评测的共识、搜索摘要或研究者自己的判断写成用户已经确认的观点。
- 不把“继续”“好的”等一般性回应解释为跳过盲点筛选或立场确认的授权。
- 不改变用户评价的谓词和力度：“还可以”不能写成“很流畅”，“有印象”不能写成“不会忘”。
- 不因结构完整而补齐用户并不关心的画面、音乐、剧情、性能等栏目。
- 不模仿用户的错别字、语音转写重复和偶发语病；保留自然节奏与词汇，做必要的可读性整理。
- 不把文章锁在与前作的比较中。先回答本作自身是什么、想做什么、做到了什么。
- 不默认把研究过程、来源列表或“技能如何工作”的说明写进可发布正文。
