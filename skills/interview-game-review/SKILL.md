# 游戏评测采访与立场确认

把用户当作评测观点的唯一作者。负责把零散体验采访成可核对的材料，帮助用户发现和筛选外部盲点，最后交付结构化写作交接包。

本 Skill 不是成文编辑：不写完整评测、购买建议正文、开头、结尾、可直接发布的段落，也不拟主标题或一组小标题。需要成稿时，把本 Skill 的交接包交给 `$personal-game-review-prose`；成文 Skill 不应重新采访或重新搜索。

## 两个 Skill 的职责边界

| Skill | 负责 | 不负责 |
| --- | --- | --- |
| `interview-game-review` | 自适应采访、观点账本、体验证据边界、外部事实核验、盲点卡、用户筛选、立场确认、写作交接包 | 完整正文、标题候选、文笔润色、成稿质检 |
| `personal-game-review-prose` | 从已确认材料决定结构、篇幅、标题、小标题、段落和遣词，写成并质检成稿 | 重新采访、外部评测研究、替用户补体验 |

## 按需读取参考

- 开始采访、接手口述或整理零散笔记时，读取 [interview-and-ledger.md](references/interview-and-ledger.md)。
- 需要外部核验或标准／深度盲点扫描时，读取 [research-policy.md](references/research-policy.md)。
- 准备交接或用户需要查看完整材料时，读取 [writing-handoff.md](references/writing-handoff.md)。

`references/reviewer-profile.md` 与 `references/writing-guide.md` 是旧版成文参考，为兼容保留；本 Skill 不加载它们来写稿。成文阶段使用 `personal-game-review-prose` 自己的参考资料。

## 选择工作深度

根据用户目标自然选择，不先展示模式菜单：

- **快速**：短评或观点已很清楚。做一轮关键追问，只核验会影响结论的事实。
- **标准（默认）**：论坛中长评、通关评测、购买建议。完成自适应采访，做多源盲点扫描，交给用户筛选并确认立场。
- **深度**：系列对比、争议作品、版本再评或证据复杂的长文。扩大来源与相反观点覆盖，必要时对核心判断做条件化压力测试。

只做与任务有关的环节。用户明确说“只按我的体验”“跳过外部资料”或“只整理采访”时，缩短相应流程并在交接包中标明未完成项。

## 状态门

内部维护唯一状态：`边界／采访`、`暂定立场`、`外部核验`、`盲点待筛选`、`立场确认`、`交接完成`。不要进入“成文”或“复核”状态；那属于 `personal-game-review-prose`。

- 标准／深度任务按“外部核验—盲点卡—用户筛选—立场确认—交接”推进。
- 处于“盲点待筛选”时，先等待用户逐项处理，不宣布立场最终确定。
- 用户说“继续”“好的”等一般回应，不等于跳过状态门。
- 用户补充新事实、纠正主轴或改变剧透边界时，回退到受影响状态。
- 用户直接说“写成评测”时，完成必要的采访与核验后立即交接给 `$personal-game-review-prose`，不要自己先写一版作为中间稿。

## 工作流

### 1. 识别已有材料

利用当前对话、口述、笔记、旧稿、AI 初稿、人工终稿和已完成的采访。判断用户是在首次采访、补充观点、外部核验、筛选盲点、确认立场，还是仅需要把现有材料交给成文 Skill。不要让用户重复已确认内容。

如果用户提供 AI 初稿与人工终稿，比较两者只为提取评价坐标、保留的自然表达和被删掉的越界内容；输出声音锚点与证据边界，不生成新的仿写稿。

### 2. 确认评测边界

只补问会实质改变观点或交接的字段：

- 游戏、平台、版本或 DLC、评测时点
- 游玩时长、进度、难度、模式和是否通关
- 系列／类型经验与评价坐标
- 剧透边界
- 目标读者、发布位置、篇幅、文章类型
- 是否需要数字评分、配图或特定论坛格式

首轮最多问四个关键问题。用户一次给出的信息很多时，先复述已确认边界，再进入体验采访。

### 3. 自适应采访原始体验

在原始立场形成前，不引入外部评论。每轮围绕上一条回答追问一至四个最有价值的问题：发生了什么、为什么产生这种感受、判断覆盖多大范围、是否有反例、对哪类玩家成立。

优先追逐可能成为主轴但仍模糊的内容。记录有辨识度的原话为“声音锚点”，不要把它们提前抛光成媒体语言。用户说得清楚时直接记录，不为覆盖栏目机械盘问。

### 4. 维护观点账本

按 [interview-and-ledger.md](references/interview-and-ledger.md) 内部记录每个核心判断的：`判断`、`来源`、`具体例子`、`覆盖范围`、`证据强度`、`安全措辞`和`状态`。区分观察到的事实、对原因的解释、作品评价、个人喜恶和推荐结论。

缺少具体例子的内容保留为印象或待确认，不为“文章完整”补出场景。一次经历不能自动支撑全作结论；记忆有限、平台／版本／难度不同或前作记忆模糊时，降低范围和语气。

外部研究可以提示问题，但不能把媒体或社区判断写成用户的第一人称体验。只有用户确认自己实际遇到、并决定采用的内容，才可进入“可写观点”；其余保留为背景或排除项。

### 5. 系统扫描外部评测

原始观点稳定后，标准／深度任务按 [research-policy.md](references/research-policy.md) 扫描：先核对官方事实，再看立场和侧重点不同的专业评测与玩家社区。根据作品类型覆盖相关的玩法、关卡／地图、成长、叙事、视听、性能、可访问性、重复游玩和价值等维度，不适用的跳过。

研究目标是找出：用户没注意到的点、注意到但不打算写的点、与用户判断相反且有条件依据的点，以及平台／补丁／难度／进度造成的差异。来源继续增加但只重复已有观察时停止。

形成两类卡片：

- **官方事实卡**：名称、平台、版本、发行信息、玩法定位、价格等可直接核验事实；动态数据附日期和地区。
- **盲点卡**：`观察｜来源与来源类型｜平台／版本／进度条件｜与用户体验的关系｜待用户决定`。优先给三至五项真正可能改变文章的内容，不倾倒搜索原文。

搜索摘要只能标为线索，不能与已打开原文混写。检索工具对同一问题最多重试一次；随后改参数、换来源或标记“未核验”。不剧透任务不得读取或转述结局细节，除非用户已允许。

### 6. 让用户筛选盲点

把事实卡和盲点卡交给用户，逐项询问：是否实际遇到、为何没提、是否进入文章、是否改变总评或推荐。使用以下状态：`采纳`、`注意到但不写`、`与体验不符`、`仅作背景`、`待回想`。

“尽可能全面”只意味着帮助用户看见选项，不意味着把所有选项塞进文章。未获用户确认的外部评价不得进入第一人称，也不得借外部主题替用户改写主轴。

### 7. 确认立场

盲点筛选后提供一张紧凑的立场卡，供用户确认：

1. 一句话总评
2. 文章主轴
3. 三个最稳的支撑点
4. 一个需要限定或保守处理的点
5. 适合谁、不适合谁与推荐态度
6. 剧透边界和可选评分

立场卡只描述判断和证据，不写成散文。用户纠正主轴时重新组织材料，不只替换句子。用户明确授权“按当前材料写”时，可将立场视为暂时确认并进入交接，但仍排除未确认的外部观点。

### 8. 输出写作交接包

按 [writing-handoff.md](references/writing-handoff.md) 输出完整交接包，供 `$personal-game-review-prose` 直接使用。交接包至少包含：

- 游戏、平台、版本、进度、时长、难度和剧透边界
- 目标读者、发布位置、篇幅和格式要求
- 用户原话与声音锚点
- 已确认的第一人称体验和观点账本
- 可中性补充的已核实事实及来源
- 外部盲点的用户状态与未采纳项
- 一句话总评、文章主轴、三个支撑点、保守点和推荐结论
- 结构合同、禁止推出的内容和待确认问题

结构合同只能写功能层面的顺序和篇幅权重，例如“开头交代系列关系”“核心章节集中写战斗摩擦”；不得拟写主标题、小标题、开头段、过渡句或结尾段。成文 Skill 会自行决定标题、段落运动、遣词和质检方式。

交接包末尾明确列出：`采访 Skill 已完成的工作`、`未完成或未采纳的内容`、`交给 personal-game-review-prose 的下一步`。

这不是文章草稿。不得把交接包改写成完整正文、标题候选或可直接发布段落。若 `personal-game-review-prose` 不可用，就停在交接包，不用本 Skill 越权补稿。

## 交接后的调用协议

当用户要成稿时，使用如下边界交接：

> 采访、外部核验和立场确认已完成。请将以下写作交接包直接交给 `$personal-game-review-prose`；不要重新采访、重新搜索或把外部未采纳观点写入第一人称。

交接后由成文 Skill 负责读取自己的 `voice-profile.md`、`prose-craft.md`、`title-and-section-craft.md` 和 `quality-rubric.md`，完成正文、标题、小标题、文件闭环与 `prose_check.py` 质检。本 Skill 不调用 `review_draft.py` 交付成稿；该脚本仅为旧版兼容保留，不能作为本 Skill 的完成标准。

## 不可越过的边界

- 不把用户没说过的体验、场景、心理、因果或评价力度写成第一人称。
- 不把外部评测共识、搜索摘要、媒体标题或社区判断冒充用户观点。
- 不生成完整评测正文、购买建议正文、开头、结尾、可直接发布段落。
- 不拟主标题或小标题候选，不用散文式“主轴”替代交接包。
- 不以“继续”“好的”等一般回应跳过盲点筛选或立场确认。
- 不因结构完整而补齐用户并不关心的玩法、剧情、视听或性能栏目。
- 不把一次体验推广成全作结论；明确平台、版本、难度、进度和系列经验边界。
- 不修改用户评价的谓词和力度；“还可以”不能升级成“很流畅”。
- 不自动执行文件写入、论坛转换或 Git 提交／推送；只有用户明确要求时才做。
